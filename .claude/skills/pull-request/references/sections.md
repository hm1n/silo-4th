# 템플릿 섹션별 작성 기준

`.github/pull_request_template.md`의 섹션마다 쓸 것과 쓰지 않을 것을 정리한 문서입니다. PR 본문을 쓰기 전에 읽습니다.

## 섹션별로 쓸 것과 쓰지 않을 것

| 섹션 | 쓸 것 | 쓰지 않을 것 |
| --- | --- | --- |
| `Closes` 줄 | 브랜치의 티켓 ID. 예: `Closes 4-42` | `Part of`, 다른 티켓 ID |
| 결과 | 이 티켓으로 무엇이 가능해졌는지 `~해요` 체 한 문장 | 파일 이름, 함수 이름, 구현 방식 |
| 바꾼 내용 | 무엇을 어디서 어떻게 바꿨는지. 선택 이유가 필요하면 짧게 덧붙입니다 | 티켓에 있는 배경 설명 |
| 하지 않은 일 | 일부러 범위에서 뺀 일과 그 이유, 다음 티켓으로 미룬 일 | 이미 한 일 |
| 영향 | 영향받는 기능, 그대로 유지한 동작, 배포 후 확인할 것 | 바꾼 내용의 반복, 배포 전에 할 설정 |
| 확인 방법 | 실제로 실행한 검사와 결과, 직접 확인한 화면 | 실행하지 않은 검사 |
| 배포할 때 필요한 작업 | 추가한 환경 변수 키, DB 마이그레이션, 외부 서비스 설정 | 환경 변수 값, 비밀 키 |
| 리뷰 포인트 | 다시 봐야 할 결정과 위험한 지점 세 개 이내 | 바꾼 내용 요약, 리뷰 도구의 실행 결과 |
| 체크리스트 | 확인을 마친 항목만 체크 | 템플릿에 없는 항목 |

---

## 문체 예시

### 결과

- 한 문장으로, 사용자나 팀이 이제 무엇을 할 수 있는지로 설명합니다.
- 파일 이름, 함수 이름, 라이브러리 이름을 쓰지 않습니다. Sentry, Vercel 같은 서비스 이름은 써도 됩니다.

- 나쁜 예: `instrumentation.ts와 lib/sentry.ts로 @sentry/nextjs를 초기화했습니다.`
- 좋은 예: `서비스에서 오류가 나면 Sentry에 기록되고, PO가 메일로 바로 알 수 있어요.`

### 불릿 항목

- `추가`, `변경`, `제거`, `분리`, `적용`, `확인`처럼 한자어 명사를 먼저 찾습니다.
- 한 항목에는 한 가지만 씁니다. 이유나 파일 경로가 필요하면 한 단계 들여 쓴 하위 불릿으로 씁니다.

나쁜 예:

```
- 서버와 브라우저에서 Sentry를 초기화하도록 instrumentation 파일을 추가했습니다.
- 세션 리플레이는 넣지 않음
```

좋은 예:

```
- 서버, edge, 브라우저의 Sentry 초기화 추가
  - `instrumentation.ts`, `instrumentation-client.ts`
- 세션 리플레이 제외
  - 학습자 화면 녹화 방지
```

### 대시, 가운뎃점, 괄호

- 대시 `—`, `–`와 가운뎃점 `·`을 쓰지 않습니다. 나열은 쉼표로 합니다.
- 괄호로 설명을 덧붙이지 않습니다. 괄호에 넣고 싶은 내용은 하위 불릿으로 내립니다.
- 하위 불릿은 공백 두 칸으로 들여 쓰고, 명사로 끝나게 요약합니다.
- 코드 span 안의 괄호와 기호는 그대로 둡니다.

나쁜 예:

```
- 환경 변수 검증 추가 (`lib/env.ts`) — 빠진 키를 빌드 때 발견
- 서버·브라우저 설정 통합
```

좋은 예:

```
- 환경 변수 검증 추가
  - `lib/env.ts`
  - 빠진 키를 빌드 때 발견
- 서버, 브라우저 설정 통합
```

## 하지 않은 일

AI 리뷰는 이 섹션을 보고 범위 밖의 지적을 거릅니다. 티켓 완료 조건 중 이번 PR에서 처리하지 않은 것이 있으면 반드시 여기 적고, 그래도 티켓을 닫아도 되는지 사용자에게 확인합니다.

---

## 영향

이 PR이 다른 영역에 미치는 영향을 씁니다. 회귀를 걱정해야 할 범위를 좁혀 주는 섹션입니다.

| 소제목 | 쓰는 내용 |
| --- | --- |
| 영향받는 기능 | 이 변경으로 동작이 달라질 수 있는 기능과 화면 |
| 바뀌지 않는 동작 | 영향받는 기능 안에서 일부러 그대로 둔 동작. 바뀌었다고 오해하기 쉬운 것을 먼저 씁니다 |
| 배포 후 확인할 것 | 배포한 뒤 실제 화면이나 Sentry, DB에서 확인해야 할 것 |

- 항목마다 한 줄로 씁니다. 이유를 길게 풀지 않고, 필요하면 하위 불릿 하나로 덧붙입니다.
- 소제목 줄은 지우지 않습니다. 해당 내용이 없으면 그 아래에 "없음"이라고 씁니다.
- 영향받는 기능은 diff에서 바뀐 파일을 import하는 곳까지 확인해 찾습니다. 확인하지 못했으면 `확인 필요`로 표시합니다.

```
영향받는 기능

- 서버, edge, 브라우저의 모든 오류 처리
  - `instrumentation.ts`, `instrumentation-client.ts`
- 렌더링 중 처리하지 못한 오류가 나면 보이는 화면
  - `app/global-error.tsx`

바뀌지 않는 동작

- 기존 페이지와 API의 응답 유지
  - Sentry는 오류 기록만 담당

배포 후 확인할 것

- `/sentry-check` 오류 발생 시 Sentry 이벤트 수신과 PO 알림 메일 확인
```

## 확인 방법

체크박스 뒤에 상세 내용을 쓸 때는 소제목을 먼저 넣습니다. 체크박스와 상세 항목이 모두 `-`로 시작하면 두 목록이 하나로 묶여 체크박스 사이가 넓어집니다.

```
- [x] `npm run check` 통과

**실행 결과**

- `/sentry-check` 페이지 오류 발생 후 Sentry 이벤트 수신 확인
```

## 배포할 때 필요한 작업

배포하기 전이나 배포하는 중에 해야 할 설정을 씁니다. 배포한 뒤에 확인할 것은 영향 섹션에 씁니다.

템플릿의 소제목 줄 아래 목록에 diff에서 찾은 내용을 채웁니다. 소제목 줄은 지우지 않고, 해당하는 것이 없으면 그 아래에 "없음"이라고 씁니다.

| 소제목 | 찾을 곳과 쓰는 내용 |
| --- | --- |
| 환경 변수 | `lib/env.ts`, `.env.example`의 변경. 키 이름만 쓰고 Vercel 환경 변수에도 넣어야 한다고 적습니다 |
| DB 마이그레이션 | `lib/db/schema.ts`, `drizzle/` 변경. 실행할 명령과 순서를 적습니다 |
| 외부 서비스 설정 | Sentry, OAuth 앱, Neon처럼 코드 밖에서 해야 하는 설정 |

## 리뷰 포인트

리뷰하는 사람이나 AI 리뷰 도구가 먼저 봐야 할 곳을 알려 줍니다. 리뷰 도구의 실행 결과는 PR 댓글에 남으므로 본문에 옮겨 적지 않습니다.

- 모두 합쳐 세 개 이내로 쓰고, High, Medium, Low 순서로 놓습니다.
- 등급마다 하나씩 채울 필요는 없습니다. 해당하는 내용이 없는 등급은 지우고, 같은 등급이 둘이면 등급 줄을 한 번 더 씁니다.
- 각 항목은 무엇을 봐 달라는지를 명사로 끝나는 불릿 한 줄로 쓰고, 왜 위험한지는 그 아래 하위 불릿으로 씁니다.
- 바꾼 내용을 다시 요약하지 않습니다.

| 등급 | 쓰는 내용 |
| --- | --- |
| 🔴 High | 사용자 경험, 데이터, 개인정보, 배포에 영향을 주는 결정 |
| 🟡 Medium | 상태가 어긋나거나 오류가 날 수 있는 구조와 경로 |
| 🟢 Low | 검증 방식이나 구현 선택이 충분한지 |

등급 줄 다음에 빈 줄을 두고 불릿을 씁니다.

```
🔴 High

- `dataCollection` 설정의 질문 원문, 이메일 전송 차단 여부
  - 학습자 정보가 외부 서비스로 나가는 지점

🟡 Medium

- 세 런타임의 `sentryOptions` 공용 사용 시 런타임별 설정 누락 여부
```

## 체크리스트

| 항목 | 체크하는 조건 |
| --- | --- |
| 규칙을 끄는 주석과 `any` | diff에서 `eslint-disable`, `@ts-ignore`, `any`를 검색해 없을 때 |
| 질문 원문과 이메일 | 로그, Sentry 호출, `_docs` 변경을 확인했을 때 |
| ADR과 `dev-rules.md` | 규칙이나 설계 변경이 없거나, 있고 두 문서에 반영했을 때 |
| `_docs/log.md` | `_docs` 변경이 없거나, 있고 `log.md`에 줄을 추가했을 때 |

조건을 확인하지 못한 항목은 체크하지 않고 그대로 둡니다. 항목을 지우지 않습니다.

---

## 같은 내용을 여러 섹션에 반복하지 않습니다

- 결과에는 무엇이 가능해졌는지만 쓰고, 어떻게 했는지는 바꾼 내용에 씁니다.
- 환경 변수와 마이그레이션은 배포할 때 필요한 작업에만 씁니다. 바꾼 내용에서는 "환경 변수 추가" 정도로만 언급합니다.
- 검사 결과는 확인 방법에만 씁니다.
- 배포 전 설정은 배포할 때 필요한 작업에, 배포 후 확인은 영향에 씁니다.
- 영향받는 기능에는 기능 이름만 쓰고, 어떻게 바꿨는지는 바꾼 내용에 씁니다.
