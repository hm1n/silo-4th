02 화면 흐름은 다른 기기나 브라우저에서 들어와도 같은 학습자로 이어지도록 정했다. 학습자를 구분하지 못하면 다음 날 확인과 내 이해 기록을 보여 줄 수 없다. (근거: [02 화면 흐름](https://linear.app/silo0/document/02-화면-흐름-6dbdadb44bbb) 흐름 1)

01 브리프는 처음에 로그인을 만들지 않도록 정했고, 개발자는 이메일 입력과 서명 쿠키로 학습자를 유지하기로 했다. 이 방식에서는 다른 사람의 이메일을 입력하면 그 사람의 기록에 이어진다. 개발자가 이 문제를 PO와 논의해 소셜 로그인을 넣기로 했다. 01 브리프의 2026-10-30 수정 전 버전은 Linear 문서 기록에서 볼 수 있다. (근거: [01 브리프](https://linear.app/silo0/document/01-브리프-5fa343785a20) "만드는 것과 만들지 않는 것", `raw/2026-10-30-social-login-decision.md`)

인증 도구는 Next.js 16 호환, 공급자 지원, Neon과 Drizzle 연결, 타입 안전성을 기준으로 고르기로 했다. 이슈 4-48은 우선 Google 로그인만 만들되, 카카오와 네이버를 나중에 설정만으로 추가할 수 있는 구조를 요구한다. (근거: `raw/2026-10-30-social-login-decision.md` "보류", [Linear 4-48](https://linear.app/silo0/issue/4-48) "범위")

2026-11-02에 확인한 사실은 다음과 같다.

- Auth.js는 2025년 9월에 Better Auth 팀으로 넘어갔고, 보안 수정만 이어 간다. (근거: [Auth.js is now part of Better Auth](https://github.com/nextauthjs/next-auth/discussions/13252))
- App Router용 Auth.js v5는 아직 베타다. npm의 `next-auth@beta`는 `5.0.0-beta.32`이고, `latest` 태그는 v4인 `4.24.15`다. (근거: 2026-11-02 `npm view next-auth dist-tags`, [Auth.js 보안 업데이트 2026년 7월](https://better-auth.com/blog/security-update-july-2026))
- Better Auth의 최신 안정판은 `1.7.15`다. peer 범위에 `next` `^16.0.0`과 `drizzle-orm` `^0.45.2`가 들어 있어, 저장소의 `next` `16.4.3`, `drizzle-orm` `0.45.4`와 맞는다. (근거: 2026-11-02 `npm view better-auth dist-tags peerDependencies`)
- Neon Auth는 Better Auth를 바탕으로 만들었지만, 관리형 SDK가 제공하는 소셜 로그인은 Google, GitHub, Vercel 세 가지다. 다른 공급자를 쓰려면 Better Auth를 직접 운영해야 한다. (근거: [Neon Auth 문서](https://neon.com/docs/ai/skills/neon-auth/SKILL.md), [Neon Auth 로드맵](https://neon.com/docs/auth/roadmap.md))

## 결정

소셜 로그인으로 학습자를 구분한다. 공급자는 우선 Google 하나로 하고, 인증 도구는 Better Auth를 Drizzle 어댑터로 우리 Neon DB에 연결해 쓴다.

Better Auth를 고른 이유는 세 가지다.

- 설정에서 타입이 추론된다. 학습자에 덧붙이는 필드와 세션의 타입을 손으로 선언하지 않아도 되므로, 0001의 원칙대로 잘못된 사용을 `npm run check`가 잡는다.
- Next.js 16을 공식 지원 범위에 두고, 정식 버전으로 개발이 이어지고 있다.
- Auth.js가 Better Auth로 넘어가 새 기능 개발이 멈췄으므로, 새로 시작하는 프로젝트가 Auth.js를 고를 이유가 적다.

## 결과

- 본인만 자기 기록에 들어갈 수 있어, 다른 사람의 이메일로 기록이 섞이는 문제가 사라진다.
- 학습자는 Better Auth의 `user`, 로그인 계정은 `account`에 대응한다. `account`에는 공급자와 공급자 계정 ID가 들어가므로, 학습자를 이메일이 아닌 공급자 계정 ID로 찾는다는 4-48의 원칙을 지킬 수 있다. 시험 날짜, 저장 동의, 출처는 `user`에 필드를 덧붙이거나 별도 테이블로 두고, 어느 쪽인지는 4-11 기록 구조 회의 결과에 맞춘다.
- 카카오와 네이버는 Better Auth가 공급자로 지원하므로, 설정과 환경 변수를 더해 추가한다. 추가 절차는 [로그인 공급자 추가 절차](../social-login-providers.md)에 있다.
- 공급자마다 OAuth 앱을 등록해야 한다. Google OAuth 앱이 테스트 상태면 등록한 테스트 사용자만 로그인할 수 있으므로, 11/5 학습자 공개 전에 운영 상태로 바꿔야 한다.
- 출처 `?from=` 값을 로그인 이동 중에 잃지 않게 하는 일과 `from=test` 테스트 학습자 구분은 이슈 4-49에서 정한다.
- 소셜 계정에서 받는 개인 정보인 이름, 이메일, 프로필 사진 중 무엇을 저장하고 어디에 보내지 않을지 정해야 한다. 이메일은 11/15 설문 발송에 필요하다. (근거: [03 상세 일정](https://linear.app/silo0/document/03-상세-일정-1f1a08402713) "발표 뒤")

구현을 시작할 때 확인하기로 한 항목은 2026-11-02 4-48 구현에서 다음과 같이 확인했다.

- **`neon-http` 트랜잭션.** Better Auth Drizzle 어댑터의 `transaction` 기본값이 `false`라 `neon-http`에서도 오류 없이 학습자와 계정을 만든다. 그런데 이 상태에서는 계정 저장만 실패해도 학습자가 남고, 계정 자동 연결이 꺼져 있어 그 학습자는 다시 로그인할 수 없다. 커밋 전 코드 리뷰에서 이를 찾아 [0003](0003-neon-postgres-drizzle.md)에 적은 대로 드라이버를 Pool 방식으로 바꾸고 `transaction: true`를 켰다. test 브랜치에서 계정 저장만 실패하게 만들면 트랜잭션을 켰을 때 학습자 행이 남지 않는다.
- **계정 자동 연결.** `account.accountLinking.enabled`를 `false`로 두어 껐다. 그런데 `learner.email`이 고유값이라, Google로 가입한 이메일로 다른 공급자에 로그인하면 새 학습자를 만들지 않고 `account_not_linked`로 거절한다. Linear 4-48 "예외 상황"은 이 경우 다른 학습자로 만든다고 적고 있어 서로 다르다. 카카오를 도입하기 전에 PO가 합칠지 정할 때 함께 정한다. `확인 필요`
- **이메일 필수.** Better Auth는 `user.email`을 필수 고유값으로 둔다. Google은 이메일을 주므로 이번 범위에는 문제가 없다. 비즈 앱 심사 전의 카카오는 이메일을 주지 않아 카카오를 붙일 때 대체 값이 필요하다. `확인 필요`

2026-11-02 커밋 전 코드 리뷰에서 다음을 정했다. 결정한 사람은 개발자다.

- **세션은 7일 동안 쓰지 않으면 만료한다.** Better Auth 기본값인 `expiresIn` 7일, `updateAge` 1일을 그대로 쓴다. 비교한 기준은 Better Auth 기본 7일, Auth.js 기본 30일, NIST 인증 지침의 가장 낮은 보증 수준 30일이다. 30일로 늘리는 방법도 검토했지만, 기간보다 연장이 쿠키에 반영되지 않는 것이 문제였다.
  - 원인: 서버 컴포넌트는 쿠키를 쓸 수 없다. `/`에서 세션을 조회하면 DB 만료일만 늘어나고, 그 뒤의 요청은 이미 연장된 것으로 보고 쿠키를 새로 쓰지 않았다. 그래서 학습자가 매일 와도 쿠키가 로그인 7일 뒤 만료됐다.
  - 처리: `findLearner`는 `disableRefresh`로 세션을 연장하지 않는다. 루트 레이아웃의 `SessionRefresh`가 Better Auth 클라이언트의 `useSession`으로 페이지를 처음 열 때와 탭으로 돌아올 때 브라우저에서 세션을 확인하고, 마지막 연장 뒤 하루가 지났으면 Better Auth가 DB 만료일과 쿠키를 함께 7일로 늘린다.
  - 확인: test 브랜치에서 남은 기간 5일인 세션을 만들어, 고치기 전에는 쿠키를 새로 받지 못하고 고친 뒤에는 `Max-Age=604800` 쿠키를 받는 것을 확인했다.
- **인증 오류는 정리한 메시지만 남긴다.** DB 오류 메시지에 토큰과 IP가 담기므로 라우트 핸들러와 `findLearner`에서 예외를 잡아 정리한다. 로그인 중 오류가 나면 빈 500 화면 대신 `/?error=internal_server_error`로 돌아와 다시 시도 안내를 본다. 처리 방식은 [0005](0005-sentry-error-monitoring.md)에 있다.
- **로그인과 로그아웃 버튼은 실패를 알린다.** 요청하는 동안 버튼을 비활성화하고, 실패하면 다시 시도 안내를 보여 준다. 로그아웃은 성공했을 때만 `router.refresh()`로 화면을 다시 그린다.

## 다시 검토할 조건

- `neon-http`와의 트랜잭션 문제를 드라이버 교체로도 풀 수 없으면 인증 도구를 다시 본다.
- 만드는 기간 안에 OAuth 등록이나 운영 전환을 마칠 수 없으면 범위를 PO와 다시 정한다.
- PO가 Google과 카카오 계정을 한 학습자로 합치기로 하면, 계정 연결 설정과 이메일 처리 방식을 다시 본다.
