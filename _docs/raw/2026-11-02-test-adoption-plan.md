# AI 주도 개발 테스트 도입 계획서

작성일: 2026-11-02
대상: Next.js 기반 풀스택 서비스

---

## 1. 도입 배경과 목적

AI로 개발하면 코드가 빠르게 늘어나지만, 그 코드가 의도대로 동작하는지 사람이 매번 직접 확인하기는 어렵습니다. 테스트 코드는 AI가 만든 코드를 자동으로 검증하는 기준 역할을 합니다.

테스트가 해결하는 문제는 다음과 같습니다.

- AI가 만든 코드가 요구사항대로 동작하는지 자동으로 검증합니다.
- AI가 기존 코드를 수정하다 다른 기능을 망가뜨리면 테스트 실패로 바로 알 수 있습니다.
- 테스트가 명확한 요구사항이 되어 AI에게 "이 테스트를 통과하게 만들어줘"처럼 정확하게 지시할 수 있습니다.

### 해결해야 할 문제

AI가 코드와 테스트를 함께 작성하면, 구현에 맞춰 테스트를 끼워 맞추는 일이 생깁니다. 이전 프로젝트에서는 요청하지 않아도 AI가 테스트를 계속 추가해 1000개가 넘었고, 그중 상당수는 중복되거나 의미가 약한 테스트일 가능성이 높습니다.

이 계획서의 목적은 **테스트가 AI를 검증하는 기준으로 제대로 작동하도록** 역할과 규칙을 정하는 것입니다.

---

## 2. 핵심 원칙

1. **테스트 케이스는 사람이 정합니다.** 어떤 상황에서 어떤 입력에 어떤 결과가 나와야 하는지는 사람이 결정하고 확정합니다.
2. **AI는 확정된 케이스를 코드로 옮기기만 합니다.** 케이스 문서에 없는 테스트는 작성하지 않습니다.
3. **확정된 테스트는 AI가 수정하지 않습니다.** 테스트가 실패하면 테스트가 아니라 구현 코드를 고칩니다.
4. **기능이 바뀌면 문서가 먼저 바뀝니다.** 사람이 케이스 문서를 수정하고 커밋한 뒤 테스트 코드를 고칩니다.
5. **테스트는 개수보다 범위가 중요합니다.** 핵심 로직과 주요 흐름을 빠짐없이 검증하는지가 기준입니다.

---

## 3. 테스트 유형과 역할

| 유형 | 검증 대상 | 예시 |
| --- | --- | --- |
| 단위 테스트 | 함수 하나의 입력과 출력, 예외 경우 | 금액을 인원수로 나눌 때 나머지 처리, 할인과 쿠폰 동시 적용, 이메일 형식 검사, 날짜 표시 변환 |
| 통합 테스트 | 여러 모듈이 맞물리는 지점 | 정산 결과 저장 API 호출 시 DB에 올바르게 기록되는지, 로그인 상태에서만 수정 요청이 성공하는지 |
| E2E 테스트 | 사용자 흐름 전체 | 회원가입부터 로그인까지, 모임 생성 후 금액 입력하고 정산 결과 화면이 뜨기까지 |

### 단위 테스트와 E2E의 관계

E2E 흐름이 실행되면 그 안의 단위 로직도 함께 실행되지만, 둘은 포함 관계가 아닙니다.

- E2E는 대표적인 한두 가지 입력으로 흐름이 끝까지 이어지는지만 확인합니다.
- 예외 경우와 경계값은 단위 테스트에서만 꼼꼼히 확인할 수 있습니다.
- E2E가 실패하면 원인 위치를 찾기 어렵고, 단위 테스트는 실패한 함수를 바로 알려줍니다.

따라서 두 테스트는 서로 다른 역할로 함께 둡니다.

---

## 4. 핵심 로직과 주요 흐름 선정 방법

### 1단계: 주요 흐름 뽑기

PRD에서 사용자가 서비스에서 반드시 해내야 하는 행동을 3~5개만 뽑습니다. 이것이 E2E 테스트 대상입니다.

### 2단계: 핵심 로직 표시하기

각 흐름을 따라가며 아래 질문에 해당하는 로직을 표시합니다. 이것이 단위 테스트 대상입니다.

- 틀리면 **돈** 계산에 문제가 생기는가
- 틀리면 **데이터**가 잘못 저장되거나 사라지는가
- 틀리면 **권한**이 없는 사람이 접근할 수 있는가
- 여러 화면에서 **공통으로 쓰이는** 변환 로직인가

### 3단계: AI 초안과 사람 확정

PRD와 코드를 AI에게 주고 후보 목록을 뽑게 한 뒤, 사람이 영향도가 큰 순서로 골라 확정합니다.

---

## 5. 테스트 케이스 관리

### PRD와의 관계

PRD와 테스트 케이스 문서는 따로 관리합니다. PRD는 무엇을 왜 만드는지 설명하고, 테스트 케이스는 기능이 맞게 동작하는지 판단하는 기준이라 목적과 수정 주기가 다릅니다.

대신 PRD의 기능마다 번호를 붙이고, 테스트 케이스에 같은 번호를 적어 연결합니다.

### 케이스 작성 형식

모든 케이스는 아래 형식으로 통일해 다른 직군도 코드 없이 읽을 수 있게 합니다.

> 어떤 상황에서, 무엇을 하면, 어떤 결과가 나온다.

### 노션 데이터베이스 구조

단위, 통합, E2E 케이스를 하나의 데이터베이스에서 관리하고 유형 속성으로 구분합니다. 한 기능 번호에 모든 유형의 케이스가 연결되어, 기능별 검증 범위를 한 화면에서 확인할 수 있습니다.

| 속성 | 타입 | 설명 |
| --- | --- | --- |
| 케이스 ID | 제목 | 예: TC-001 |
| PRD 기능 번호 | 텍스트 또는 관계 | PRD의 기능 번호와 연결 |
| 테스트 유형 | 선택 | 단위, 통합, E2E |
| 상황 | 텍스트 | 테스트 전 조건 |
| 행동 | 텍스트 | 입력 또는 사용자 행동 |
| 기대 결과 | 텍스트 | 나와야 하는 결과 |
| 우선순위 | 선택 | 높음, 보통, 낮음 |
| 상태 | 선택 | 초안, 검토 중, 확정, 폐기 |
| 담당자 | 사람 | 케이스 책임자 |

E2E 케이스는 단계가 많으므로, 케이스 페이지 본문에 단계별 절차를 따로 적습니다.

### 노션 문서 구조

```
테스트 케이스 (상위 페이지)
├── 작성 규칙 안내: 문장 형식, 상태 변경 규칙
└── 테스트 케이스 데이터베이스
    ├── 보기: 단위 테스트
    ├── 보기: 통합 테스트
    ├── 보기: E2E 테스트
    ├── 보기: 기능별 그룹
    └── 보기: 저장소 반영 대상 (상태 = 확정)
```

### 저장소 동기화

AI가 참고하는 기준이 흔들리지 않도록, 상태가 확정인 케이스만 저장소의 마크다운 파일로 내보냅니다.

```
docs/test-cases/
├── unit.md
├── integration.md
└── e2e.md
```

노션에서 케이스가 수정되면 확정 후 다시 내보내고 커밋해 변경 이력을 깃으로 추적합니다.

## 6. 도구와 디렉토리 구조

### 도구 선택

| 용도 | 도구 | 선택 이유 |
| --- | --- | --- |
| 단위 테스트 | Vitest | 실행이 빠르고 TypeScript와 ESM을 바로 지원해 AI가 반복 실행하는 흐름에 적합. 서버와 브라우저 환경을 파일별로 나누기 쉬워 풀스택에 유리 |
| 통합 테스트 | Vitest + React Testing Library | 사용자가 보는 화면 기준으로 컴포넌트 검증 |
| E2E 테스트 | Playwright | 빠르고 여러 브라우저를 지원하며 무료로 병렬 실행 가능. 비동기 서버 컴포넌트 검증도 E2E로 처리 |

Next.js 공식 문서는 Jest와 Vitest를 모두 안내합니다. 이미 Jest로 구성된 프로젝트라면 유지해도 되며, 두 도구는 문법이 거의 같아 나중에 옮기기도 어렵지 않습니다.

### 디렉토리 구조

```
project/
├── src/
│   ├── utils/
│   │   ├── calc.ts
│   │   └── calc.test.ts        단위 테스트는 대상 파일 옆에 둠
│   └── components/
│       ├── SettleForm.tsx
│       └── SettleForm.test.tsx
├── e2e/                         E2E는 최상위 폴더에서 흐름별로 관리
│   ├── signup.spec.ts
│   └── settlement.spec.ts
├── docs/
│   └── test-cases/              확정된 테스트 케이스
└── CLAUDE.md                    AI 작업 규칙
```

단위 테스트를 대상 파일 옆에 두면 코드와 테스트를 함께 찾고 수정하기 쉬워 AI가 작업할 때 누락이 줄어듭니다.

## 7. AI 작업 규칙

아래 내용을 `CLAUDE.md` 같은 AI 지침 파일에 적어둡니다.

```markdown
## 테스트 작성 규칙

- 테스트는 docs/test-cases/ 에 있는 케이스만 작성한다.
- 케이스 문서에 없는 테스트가 필요하다고 판단되면 작성하지 말고 먼저 제안한다.
- 이미 작성된 테스트 코드는 수정하지 않는다. 테스트가 실패하면 구현 코드를 고친다.
- 테스트 수정이 꼭 필요하다고 판단되면 이유를 설명하고 승인을 받는다.
- 테스트 파일 이름에 케이스 ID를 주석으로 남긴다.
- 구현 세부사항이 아닌 입력과 결과를 기준으로 테스트한다.
```

### 개발 흐름

1. 사람이 PRD 기능에 맞춰 테스트 케이스를 확정합니다.
2. 확정된 케이스를 저장소에 반영합니다.
3. AI가 케이스를 테스트 코드로 옮깁니다.
4. AI가 테스트를 통과하도록 기능을 구현합니다.
5. 사람이 테스트 코드와 케이스가 일치하는지 검토합니다.

## 8. 단계별 도입 계획

| 단계 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 1단계 준비 | PRD 기능 번호 정리, 노션 데이터베이스 생성, CLAUDE.md 규칙 작성 | 데이터베이스와 규칙 파일 준비 완료 |
| 2단계 단위 테스트 | 핵심 로직 선정, 케이스 확정, Vitest 설정 후 테스트 작성 | 돈, 데이터, 권한 관련 로직 모두 테스트 통과 |
| 3단계 E2E | 주요 흐름 3~5개 확정, Playwright 설정 후 테스트 작성 | 핵심 사용자 흐름 모두 테스트 통과 |
| 4단계 통합 테스트 | API와 DB, 인증이 맞물리는 지점 케이스 추가 | 주요 API 동작 테스트 통과 |
| 5단계 정착 | 기능 추가 시 케이스 먼저 작성하는 흐름 유지 | 새 기능마다 케이스 문서가 먼저 갱신됨 |

### 점검 기준

- 모든 테스트가 케이스 ID와 연결되어 있는가
- AI가 확정된 테스트를 임의로 수정한 적이 없는가
- 케이스 문서에 없는 테스트가 늘어나고 있지 않은가
- 코드를 조금 바꿨을 때 테스트가 대량으로 깨지지 않는가
