# 03-1 진행 가이드

[상세 일정](<https://linear.app/silo0/document/03-%EC%83%81%EC%84%B8-%EC%9D%BC%EC%A0%95-1f1a08402713>)의 일을 "어떻게" 하는지 정리한 하위 문서예요. 인터뷰를 하거나, 학습셋을 만들거나, 학습자에게 주소를 알리거나, 발표를 준비할 때 해당 섹션을 열어 주세요.

## 인터뷰

### 목표와 분량

| 항목 | 내용 |
| -- | -- |
| 목표 | 프로토타입이 나오기 전에 H2(이해했다고 착각한다)를 손으로 먼저 확인하고, "자신 있었는데 틀렸다"는 순간에 학습자가 어떻게 반응하는지 봐요 |
| 대상 | SQLD를 준비하며 AI로 공부하는 사람 |
| 분량 | 6\~8명, 한 사람에 20\~30분 (통화나 화상) |
| 기간 | 10/30 (금)\~11/4 (수). 월요일과 화요일에 2\~3명씩 |
| 모집 | 금요일에 커뮤니티 모집 글을 올리고, 지인에게도 부탁해요 |
| 함께 듣는 사람 | 디자이너와 개발자가 각각 한 번 이상 함께 들어요 |

### 진행 순서

1. **최근 공부 이야기 (5분):** AI로 어떻게 공부하는지, 최근 AI 대화 기록을 함께 보며 물어요.
2. **손으로 하는 확인 (10분):**
   1. 최근 AI에게 물어본 SQLD 개념을 하나 골라요.
   2. 그 개념으로 개념 이름이 나오지 않는 문제를 보여 주기 전에 "맞힐 자신이 몇 %인가요?"를 물어요.
   3. 문제를 풀게 하고, 결과를 알려 줘요.
   4. 결과를 들었을 때의 반응을 그대로 기록해요.
3. **확인과 기록에 대한 생각 (5분):** "시험 전에 이런 확인을 해 주는 서비스가 있으면 쓰시겠어요? 언제 쓰시겠어요?"를 물어요.
4. **안내 (1분):** 목요일에 서비스가 열리면 주소를 보내 드려도 되는지 물어요.

손으로 하는 확인에 쓰는 문제는 서비스에 넣을 확인 문제 초안을 그대로 써요. 인터뷰에서 문제의 난이도와 문구도 함께 점검할 수 있어요.

인터뷰에서는 학습자의 말보다 행동을 더 믿어요. "쓰겠다"고 말한 사람이 실제로는 거의 쓰지 않는 경우가 많아요.

### 인터뷰 결과를 쓰는 곳

| 결과 | 쓰는 사람 | 쓰는 곳 |
| -- | -- | -- |
| "자신 있었는데 틀렸다"는 순간의 반응 | 디자이너 | 결과 화면의 문구와 분위기 |
| 문제가 너무 쉽거나 어려웠던 경우 | PO | 확인 문제 수정 |
| 확인을 쓰고 싶은 때 | PO, 디자이너 | 확인 화면을 띄우는 시점 |
| 기본 장면을 뒤집을 만한 내용 | PO | 그날 저녁 팀에 알려요 |

## 학습셋

SQLD 전체 범위를 화요일까지 만들기는 어려워요. 학습자가 많이 헷갈리는 단원 3\~5개로 시작해요. 단원은 10/30 (금) 오전에 PO가 정해요.

| 준비할 것 | 분량 | 만드는 방법 | 기한 |
| -- | -- | -- | -- |
| 학습 자료 | 단원 3\~5개 | AI로 초안을 만들고 PO가 검토해요 | 11/2 (월) |
| 확인 문제 | 단원마다 개념별 객관식 문제 | AI로 초안을 만들고 PO가 검토해요. 형식은 [화면 흐름](<https://linear.app/silo0/document/02-%ED%99%94%EB%A9%B4-%ED%9D%90%EB%A6%84-6dbdadb44bbb>)의 "확인 문제의 형식"을 따라요 | 11/3 (화) |

## 학습자에게 알리기

### 출처를 나눠서 기록해요

지인은 부탁을 받아서 써요. 스스로 찾아온 사람과 결과를 섞으면 "다시 오는가" 같은 신호가 실제보다 좋게 나와요. 그래서 서비스 주소에 출처를 붙여 나눠서 기록해요.

| 출처 | 서비스 주소 | 결과를 볼 때 |
| -- | -- | -- |
| 커뮤니티 | `서비스주소?from=community` | 스스로 찾아온 사람이에요. 모든 지표를 보고, "다시 오는가"는 이 집단으로만 판단해요 |
| 지인 | `서비스주소?from=friend` | 착각 비율(H2)과 확인 완료 비율(H3)을 보는 데 써요 |
| 인터뷰 참여자 | `서비스주소?from=interview` | 인터뷰에서 한 말과 실제 행동을 비교해요 |

학습자에게 공개하는 주소는 리니어에 두지 않아요. 팀원이 실수로 공개 주소로 들어가면 출처 기록이 섞여요. 팀은 테스트용 주소를 써요.

### 언제, 어디에 알리나요

| 언제 | 무엇을 |
| -- | -- |
| 11/4 (수) | 게시글, 올릴 커뮤니티 목록, 출처별 주소, 조회 수를 적을 표를 준비해요 |
| 11/5 (목) 오전 | 커뮤니티 여러 곳에 한꺼번에 올리고, 지인과 인터뷰 참여자에게 주소를 보내요 |
| 11/6 (금) 오전 | 반응이 적은 곳에 다시 알리거나, 다른 커뮤니티에 올려요 |

목요일 오전에 한꺼번에 올리는 이유가 있어요. 목요일에 들어온 학습자는 금, 토, 일, 월 4번 확인할 수 있지만, 일요일에 들어온 학습자는 월요일 오전에 한 번만 확인할 수 있어요.

게시글별 조회 수는 공부 시작 비율(H1)을 계산할 때 써요. 올린 날과 11/9, 11/14에 조회 수를 적어요.

## 만들 때의 규칙

### 기능 동결

11/4 (수) 저녁부터는 새 기능을 넣지 않고, 버그 수정과 문구 수정만 해요. 주말에는 아무도 대응할 수 없어서, 목요일과 금요일을 안정화에 써야 해요. 11/6 (금) 저녁 마지막 배포 뒤에는 배포하지 않아요.

### 테스트 학습자로 점검하기

"다음 날 확인"은 하루를 기다려야 해서, 테스트용 학습자는 날짜를 하루 당겨서 확인 화면이 뜨는지 봐요. 방법은 개발자가 정해요. 11/4 (수)에 PO와 개발자가 함께 아래를 확인해요.

* 첫 화면부터 내 이해 기록까지 끊기지 않아요
* [화면 흐름](<https://linear.app/silo0/document/02-%ED%99%94%EB%A9%B4-%ED%9D%90%EB%A6%84-6dbdadb44bbb>)의 상황별 규칙이 동작해요
* 세 가지 출처 주소로 들어가면 출처가 각각 저장돼요
* "남겨야 할 기록" 여섯 가지가 모두 남아요

## 발표와 최종 결과

### 발표와 최종 결과를 나눠요

발표(11/10)는 결과가 다 나오기 전이에요. 그래서 발표 범위를 줄이고, 서비스는 시험일(11/14)까지 열어 둬요.

|  | 발표 (11/10) | 최종 결과 (11/20) |
| -- | -- | -- |
| 데이터 기간 | 11/5\~11/9 낮 12시 (5일) | 11/5\~11/14 (10일) + 시험 뒤 설문 |
| 다루는 것 | 문제를 다시 정의한 과정, 프로토타입, 인터뷰 결과, 첫 신호 | H1\~H4 판단, 아쉬움 응답, 다음 가설 |
| 쓰는 곳 | 프로젝트 발표 | 결과와 러닝 기록, 포트폴리오 |

| 발표에서 다루는 것 | 근거 |

발표 메시지는 **"문제를 다시 정의했고, 첫 신호를 봤고, 최종 판단은 시험 뒤에 이렇게 내린다"** 예요.

### 시험 뒤 설문

시험 직후는 학습자가 "도움이 됐는지" 가장 생생하게 기억할 때예요. 그래서 시험 다음 날인 11/15 (일)에 첫 화면에서 받은 이메일로 보내요.

| 질문 | 답 형식 |
| -- | -- |
| 이 서비스를 더 못 쓰게 되면 어떠세요? | 매우 아쉽다 / 조금 아쉽다 / 아쉽지 않다 |
| 여기서 틀렸던 개념이 시험에 나왔을 때 어땠나요? | 자유롭게 |
