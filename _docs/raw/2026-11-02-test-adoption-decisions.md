# 테스트 도입 결정

## 배경

개발자가 기능 구현을 본격적으로 시작하기 전에 테스트 도구를 도입하려고, 테스트 도입 계획서를 바탕으로 검토를 요청했다. Claude가 계획서를 저장소 상태와 맞춰 본 결과, 경로가 저장소와 다르고, 케이스 원본 위치가 `_docs/CLAUDE.md`의 Linear 우선 원칙과 충돌하며, LLM 호출과 테스트 DB를 다루는 방법이 빠져 있다는 점을 짚었다.

## 정한 것

- 계획서의 핵심 원칙 다섯 가지를 따른다. 케이스는 사람이 정하고, AI는 확정된 케이스만 코드로 옮기며, 확정된 테스트는 AI가 고치지 않는다. 기능이 바뀌면 케이스 문서를 먼저 고치고, 테스트는 개수보다 범위를 기준으로 본다.
- 테스트 케이스의 원본은 노션 DB로 한다. Linear에도 비슷한 형식이 있는지 확인했지만, Linear 문서는 행마다 속성을 줄 수 없고, 이슈는 사용자 정의 필드가 없어 상황, 행동, 기대 결과를 본문 텍스트로만 둘 수 있다. 개발자가 이를 보고 노션 DB를 쓰기로 했다.
- 상태가 확정인 케이스만 저장소의 마크다운으로 내보낸다.
- 단위 테스트는 Vitest, E2E 테스트는 Playwright로 한다.
- 통합 테스트는 DB를 변경하는 서버 코드에만 둔다. Route Handler나 Server Action을 직접 호출하고 실제 테스트 DB에 남은 결과를 확인한다. Anthropic SDK는 목으로 바꾼다. 도구는 Vitest를 그대로 쓴다.
- React Testing Library로 하는 컴포넌트 테스트는 두지 않는다. 화면은 E2E가 확인하고, 화면 안의 변환 로직은 함수로 빼서 단위 테스트한다.

## 통합 테스트를 두는 이유

개발자는 처음에 단위 테스트와 E2E면 충분하다고 봤다. Claude가 다음 이유로 DB를 변경하는 지점에는 통합 테스트가 필요하다고 설명했고, 개발자가 이를 받아들였다.

- 이 서비스의 핵심 요구는 기록 여섯 가지를 빠짐없이 남기는 것이라, 계획서의 선정 기준 가운데 데이터와 권한이 가장 큰 위험이다. 이 두 가지는 서버 코드와 DB가 맞물리는 곳에서 틀린다.
- 단위 테스트에서 DB를 목으로 바꾸면 실제 저장 결과를 확인하지 못한다. E2E는 화면에 보이지 않는 기록을 확인하기 어렵고, AI 호출 실패, 중복 요청, 학습자 간 접근 같은 경우를 하나씩 흐름으로 만들면 느리고 깨지기 쉽다.
- Google OAuth는 자동화된 브라우저로 통과하기 어려워, 권한 검증을 E2E에 맡기면 인증 우회 장치에 기대는 범위가 커진다.
- `neon-http`는 대화형 트랜잭션을 지원하지 않아, 여러 기록을 한꺼번에 저장하다 실패하면 일부만 남을 수 있다. 이런 문제는 실제 DB를 대상으로 해야 드러난다.

## 정하지 않은 것

Claude가 제안했지만 개발자가 아직 정하지 않았다.

- 확정 케이스를 내보낼 저장소 경로. Claude는 `_docs/wiki/test-cases/`를 제안했다.
- 노션에서 저장소로 내보내는 방법.
- 기존 테스트 파일 수정을 막는 PreToolUse 훅.
- 테스트 이름의 케이스 ID가 케이스 문서에 있는지 검사하는 스크립트.
- Stop 훅에 테스트를 넣을지, 넣는다면 어느 유형까지 넣을지.
- 테스트 DB로 쓸 Neon 브랜치 구성과 CI.
- E2E에서 로그인을 처리하는 방법.
